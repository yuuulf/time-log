# Design

## Context

- 記録は `time_entries` に 1 行ずつ保存し、開始・終了時刻は UTC のミリ秒で持つ。日ごとの表示（「今日の記録」「過去の記録」）と集計は、開始時刻がどの日（日本時間）にあるかで記録を振り分けている（`lib/time.ts` の `dayRange`・`toDateKey`、`lib/time-entries/repository.ts` の `listEntriesBetween`）
- 記録が終わるのは `lib/time-entries/repository.ts` の 2 か所: `stopRunningEntry`（「終了」ボタン）と `startEntry` の中の自動の終了（開始・再開。再開も `startEntryAction` を通る）。時刻の修正は `updateEntry` で、入力チェック（終了は開始より後、未来は不可）は `validation.ts` で済ませてから呼ばれる
- 日本時間には夏時間がないため、1 日はいつも 24 時間

要件は `specs/time-tracking/spec.md` の「日をまたぐ記録の分割」を参照。

## Goals / Non-Goals

**Goals:**

- 分割のルール（どこで切るか・どの区間を残すか）を DB から切り離した純粋な関数にまとめ、境目の細かい場合をそこでテストする
- 終了・修正で 1 件の記録が複数行になる処理を、1 つのトランザクションで行う

**Non-Goals:**

- 画面のコンポーネントや Server Action の入出力は変えない（分割は repository の中で完結し、画面は保存後の再取得で分かれた記録を表示する）
- DB のスキーマは変えない（分けた記録どうしを結びつける列は持たない）

## Decisions

### 1. 分割の計算は `lib/time.ts` の純粋な関数にする

`splitByJstDay(startedAt: Date, endedAt: Date): { startedAt: Date; endedAt: Date }[]` のような関数を `lib/time.ts` に置く。開始日の 0 時から 24 時間ずつ進めて、各日の区間を `[max(開始, その日の 0:00:00), min(終了, その日の 23:59:59)]` とし、最後の日だけ終了時刻をそのまま使う。

- 日をまたがない記録（終了が開始と同じ日、または終了がちょうど翌日の 0:00:00）は、そのまま 1 区間を返す
- 開始がその日の 23:59:59 より後（例: 23:59:59.500）のときは前の日の区間が長さ 0 以下になるので、その区間は作らず次の日の区間から始める。ミリ秒単位でしか起きない端の場合で、失う時間は 1 秒未満
- 「その日の 23:59:59」は「翌日 0 時 − 1 秒」で求める（ミリ秒は 0）

代替案: repository の中で直接計算する → 境目の場合を DB なしでテストしにくいので採らない。

### 2. 元の記録は開始日の区間として残し、2 日目以降は新しい行を足す

元の行（id）を開始日の区間に更新し、2 日目以降の区間は同じタスク名・同じプロジェクトで新しい行を insert する。`createdAt`・`updatedAt` は処理した時刻にする。

- 元の id を残すので、一覧で編集中の行（開始日の区間）がそのまま残り、画面側の扱いが変わらない
- 開始時刻を前の日に直した場合（spec の「開始時刻を直して日をまたぐ」）も、元の行は直した開始時刻を含む日の区間になり、その日の一覧からは消えて前の日へ移る。編集していた日の一覧には新しく足した行が表示される

代替案: 元の行を最後の日の区間にする → 「終了」直後に元の行が今日に残るのは自然だが、修正のときに元の行がどの日に行くかが入力次第で変わり、ルールが分かりにくいので採らない。開始日に揃える。

### 3. 分割は repository の終了・修正の処理の中で行う

- `stopRunningEntry` と `startEntry` の自動の終了: 記録中の行を取り出し、終了時刻を決めてから分割して保存する共通の内部関数（例: `finishEntry(tx, entry, endedAt, now)`）を通す。`startEntry` は既存どおり 1 トランザクションの中で「終了（分割）→ 新しい記録の insert」を行う
- `updateEntry`: 記録中の記録はこれまでどおり分けない。終了済みの記録は、更新後の開始・終了時刻で分割し、同じトランザクションで元の行の更新と新しい行の insert を行う
- `stopRunningEntry` の戻り値は、開始日の区間（元の行）にする。呼び出し側（`stopEntryAction`）は戻り値を使っていないので影響はない

代替案: Server Action（`actions.ts`）で分割する → 終了の経路が repository に 2 つあり、テストも repository 単位で書いているので、repository に置く。

### 4. 記録中の一意インデックスとの関係

分けた行はすべて終了時刻を持つので、「記録中は 1 件まで」の一意インデックス（`time_entries_one_running_idx`）には触れない。`startEntry` では、分割（すべて終了済み）を済ませてから新しい記録中の行を insert する順序を保つ。

## Risks / Trade-offs

- [分けた記録の合計が日の境目ごとに 1 秒短くなる] → ユーザーが選んだ仕様（23:59:59 で終える）。分単位に切り捨てるため、23:00〜23:59:59 は「59分」と表示される。spec のシナリオに明記した
- [分けた記録どうしの結びつきを持たないので、片方を直してももう片方は変わらない] → 分けたあとは独立した記録として扱う仕様にする。まとめ直す操作はスコープ外
- [この変更より前に保存された日をまたぐ記録は分かれないまま残る] → 時刻を直して保存すれば分かれる。集計の「開始した日の期間にすべて含める」扱いはそのまま残す
- [修正で日をまたぐと、編集していた行が別の日へ移って一覧から消える] → 保存後の再取得でその日の区間（新しい行）が表示されるので、記録が消えたようには見えない。spec のシナリオで確認する

## Migration Plan

スキーマの変更も既存データの移行もない。デプロイ後に終了・修正したものから分割される。戻すときはコードを戻すだけでよい（分かれた記録は分かれたまま残る）。
